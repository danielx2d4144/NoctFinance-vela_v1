# 29. Testing Strategy

**Status:** Implementation architecture baseline  
**Audience:** Noct engineering team, junior developer, coding agent  
**Normative terms:** MUST = mandatory; MUST NOT = prohibited; SHOULD = recommended; OPEN = unresolved and must not be invented.

## Test layers

```text
unit and golden-vector tests
→ property/invariant tests
→ contract and WASM integration tests
→ full Vela end-to-end tests
→ recovery, reorg, load, and adversarial tests
```

Coverage percentages are secondary to invariant and branch coverage. Every financial, receipt, replay, oracle, settlement, and recovery branch is critical and MUST have positive and negative tests.

## Canonical arithmetic tests

Financial test fixtures use canonical 32-byte U256 encodings. Native `uint64`, JavaScript `number`, floating point, and `math/big` reference behavior inside production WASM are prohibited substitutes.

Golden vectors MUST cover:

- zero, one, WAD, RAY, and maximum accepted U256 values;
- non-canonical width/sign/leading-data rejection;
- checked add/subtract overflow and underflow;
- full-width `mulDivDown` and `mulDivUp`;
- WAD/RAY conversions and rounding directions;
- kink-rate boundary immediately below, at, and above optimal utilization;
- one-second, one-year, and multi-chunk index accrual;
- timestamp regression and excessive interval handling;
- scaled borrow, partial repay, and full-repay clearing;
- cross-asset liquidation USD conversion and collateral cap.

Reference vectors SHOULD be generated by an independent audited implementation and checked into the repository.

## Core invariant suite

After every generated successful transition assert:

```text
reserve.totalScaledDebt[a] = Σ account.scaledDebt[a]
accountDebt[a] = ceil(account.scaledDebt[a] × borrowIndex[a] / RAY)
borrowIndex[a] >= RAY and never decreases
stateVersion and applicable nonces never regress
receipt and operation statuses never regress
consumed receipt IDs and withdrawal IDs remain unique
Custody[a] = Ledger[a] + PendingInbound[a] + PendingOutbound[a]
```

Also assert:

- supply/release preserve total private USDC before external withdrawal;
- borrow/release use `maxLTV`, not liquidation threshold;
- liquidation eligibility uses liquidation threshold;
- debt reduction always consumes the exact captured receipt;
- native withdrawal output always has the matching atomic private-ledger debit;
- failed transitions return no new state and no withdrawal;
- derived collateral rounds down and debt rounds up.

## State-machine model tests

Generate operation sequences over all File 12 transitions:

- consume deposit/funding receipt;
- supply and release;
- borrow and borrowed-asset withdrawal;
- prepare/capture/commit repayment;
- prepare/capture/commit liquidation;
- pre-capture expiry;
- reserve accrual;
- oracle update;
- cash withdrawal.

The model MUST include duplicate delivery, stale nonces, conflicting locks, state-root changes, oracle epoch changes, and crashes between every phase.

Forbidden transitions include:

```text
PAYMENT_CAPTURED -> EXPIRED
COMMITTED -> any earlier status
CONSUMED receipt -> unconsumed
native pendingClaim delay -> private balance restoration
repayment/liquidation commit without matching receipt
risk mutation from caller-provided oracle data
```

## Unit tests

### TinyGo/WASM

Test pure functions and transition reducers without weakening production arithmetic:

```go
func TestConsumeDepositReceiptOnce(t *testing.T) {
    amount := MustAmountWad("1000")
    receipt := FinalizedDepositReceipt("receipt-1", amount)

    state1, result1 := ApplyConsumeDeposit(EmptyState(), receipt)
    state2, result2 := ApplyConsumeDeposit(state1, receipt)

    RequireAmountEqual(t, state1.Account(user).CashUSDC, amount)
    RequireStateEqual(t, state2, state1)
    RequireResultEqual(t, result2, result1)
}
```

Required unit areas:

- canonical codecs and domain hashes;
- account/reserve arithmetic;
- interest accrual;
- risk checks;
- commitment trees and app root;
- exact nonce handling;
- operation locks/statuses;
- receipt and withdrawal deduplication;
- privacy-safe errors/events;
- deanonymization report scope and encoding.

### Solidity

Foundry tests cover:

- OracleAdapter exact feed IDs and official Pyth calls;
- price positivity, exponent normalization, confidence, age/skew, and deviation breaker;
- monotonic adapter epoch and snapshot commitment;
- AbstractTrigger caller/domain restrictions;
- exact payment escrow capture and duplicate prevention;
- fee-on-transfer/rebasing-token rejection or unsupported-token guard;
- unauthorized TRUSTPROCESS attempts;
- custody ingress and official Vela integration behavior.

## Integration tests

All integration tests use `ProcessorEndpoint`; no direct-enclave shortcut is valid.

### Native withdrawal

1. Credit private cash through an authenticated finalized receipt.
2. Submit encrypted withdrawal `PROCESS` request.
3. Verify returned state debits cash and contains one withdrawal.
4. Verify accepted `stateUpdate` creates one pending claim.
5. Delay `claim()` and prove private cash is not restored.
6. Redeliver/retry and prove no second claim.
7. Claim and verify wallet delivery without another private mutation.

### Oracle/risk operation

1. Submit official Pyth EVM update data to OracleAdapter.
2. Stage encrypted borrow/release/discovery intent.
3. Verify initial PROCESS changes no financial risk state.
4. Verify trigger max-delay check and authenticated TRUSTPROCESS.
5. Verify guest accepts only a strictly newer committed epoch.
6. Verify accrual uses adapter block timestamp.
7. Verify caller/facilitator snapshot injection fails.

### Repayment

1. Borrow and accrue.
2. PREPARE exact full or partial repayment.
3. Verify no debt/liquidity mutation.
4. Capture exact on-chain payment receipt.
5. Crash/restart before commit.
6. Deliver authenticated commit.
7. Verify receipt consumption, scaled-debt reduction, liquidity credit, and lock removal once.
8. Redeliver commit and compare byte-identical stored result.

### Liquidation

Test private bounded discovery, no candidate leakage, prepare with correct cross-asset valuation, exact capture, commit, USDC pending claim, and idempotent replay. Wrong asset/amount/operation and free-liquidation attempts must fail.

## ZK tests

When custom ZK is enabled:

- flatten public inputs under the pinned maximum;
- verify all File 09 subroots/economic fields are constrained;
- bind actual Vela application ID, chain, request, actors, nonce, config, oracle, operation, receipt, and withdrawal;
- reject valid proofs paired with different returned state/output;
- measure stale-proof rate under concurrent global-root mutation;
- verify zkVerify receipt authenticity rather than trusting client JSON;
- fail closed under provider outage according to File 15.

## Recovery and chaos tests

Inject failure before and after:

- request inclusion;
- Manager pickup;
- guest result creation;
- Vela state update;
- trigger execution;
- payment capture;
- commit request and acknowledgement;
- pending-claim creation and user claim.

Also test coupled restart, unsupported partial restart, reorg, RPC partition, corrupted/missing encrypted-state version, OracleAdapter outage, Pyth breaker, and long-delayed captured commit.

Recovery succeeds only if the encrypted state matches the canonical Vela root and all invariants pass. Tests MUST NOT manufacture receipts, replay deposits into an empty ledger, or unlock captured operations.

## Privacy tests

Assert that plaintext AppEvents, trigger payloads, RPC errors, logs, metrics, crash reports, and analytics do not expose:

- borrower identity during discovery;
- balances, collateral, debt, health factor, or Merkle witnesses;
- encryption keys or proof witnesses;
- deanonymization report contents.

Timing tests compare transition classes and scan positions. Authorized `DEANONYMIZATION` reports must be scope-limited and decryptable only by the approved authority key.

## Performance tests

Follow File 28. Measure separate request inclusion, private-state finality, claim availability, wallet delivery, payment capture, and economic commit. Run realistic state sizes and mixed traffic; averages alone are insufficient.

No test hard-codes a 10 TPS or 30-second production guarantee. Release targets are approved only after p95/p99 data from the pinned deployment.

## Regression policy

Every security defect adds:

1. a minimal reproducer;
2. an invariant/property test when possible;
3. a full-path regression test;
4. a threat-model update;
5. a versioned golden vector if serialization/arithmetic changed.

Regressions for the original architecture MUST specifically preserve fixes for:

- borrow-based interest erasure;
- aggregate/account debt divergence;
- `uint64` financial overflow;
- debt reduction without payment;
- free liquidation and wrong-asset pricing;
- oracle self-freshness and replay;
- maxLTV/liquidation-threshold confusion;
- withdrawal rollback after pending-claim creation;
- incomplete commitments and stale cross-context proofs.

## CI gates

Pull requests are blocked unless:

- unit, property, invariant, integration, and serialization-vector suites pass;
- circuit public-input/constraint checks pass when applicable;
- Foundry fuzz/invariant tests pass;
- static analysis reports no unresolved critical/high issue;
- no golden commitment vector changes without an explicit schema/version migration;
- coverage for affected critical branches remains complete;
- documentation cross-reference checks find no prohibited legacy field/API.
